# Spec de Performance 01 — Render, IPC e custo de partida do Campus

Data: 2026-09-29
Escopo: auditar a performance de render do front-end (React 19 + Vite 8), do IPC (`invoke`/SQLite/Rust) e do custo de partida do shell Tauri/Wry/WebView2, e fechar as decisões que transformam o diagnóstico em trabalho executável.
Status: **especificação — nada foi implementado.** Todas as medições de tempo aqui citadas são **estimativas derivadas da leitura do código** e estão marcadas como tal; a Fase P0 existe justamente para substituí-las por número medido.

**As decisões de `docs/calendario/` continuam valendo.** Esta spec não reabre D1..D20 nem INV-1..INV-7: ela diz **como** o código que já obedece a elas precisa ser escrito para não custar um quadro de 16 ms. Onde uma decisão de performance parecesse contrariar uma regra de domínio, a regra de domínio vence e o custo se resolve por outro caminho — DP1 e DP2 são examples disso.

**Numeração.** `D*` é das specs de `docs/calendario/`. `DP*` (Decision Performance) é exclusivo desta spec. Nenhum `DP` substitui ou renumera um `D`.

## 1. Diagnóstico

## 2. Baseline e instrumentação

### 2.1 Script de medição de build (versionável, sem dependência nova)

Criar `scripts/measure-bundle.mjs` e o script `"measure:bundle": "npm run build && node scripts/measure-bundle.mjs"` no `package.json`. Ele **apenas lê `dist/assets`** e imprime, por arquivo: bytes, gzip (`zlib.gzipSync`, nível 9) e brotli, mais o total. Guardar a saída em `docs/performance/baseline/build-<data>.txt`.

Estado de referência medido em 2026-09-29 (acima, §1.1): **377.78 kB / 117.78 kB gzip** de JS, **59.75 kB / 10.86 kB gzip** de CSS, **1 chunk**.

### 2.2 Perfil React (o que responde "quem re-renderiza")

1. `npm run tauri:dev` (o shell real; `npm run dev` no Chrome serve só como iteração rápida, e o WebView2 é o alvo).
2. React DevTools → aba **Profiler** → gravar.
3. Interações a medir, uma por gravação:
   - abrir **Grade & Calendário** e esperar 65 s parado (mede o custo do relógio de `:120-123`);

4. Para cada gravação, anotar: **quantas vezes `WeekView` renderizou** e **quanto durou cada commit**. O alvo é: 0 renders de `WeekView` no caso 1 depois de P2, e **1** render por clique no caso 2.

Instalar a extensão em `tauri:dev` funciona, mas para medir produção é preciso `npm run tauri build -- --debug` (o DevTools vem ligado em debug).

### 2.3 DevTools do WebView2 (o que responde "onde o quadro foi gasto")

1. Habilitar developer mode em `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` (§2.5) para ter DevTools remoto; ou usar o DevTools embutido com `Ctrl+Shift+I` / botão direito → _Inspect_, que é o caminho padrão do Tauri no Windows — <https://v2.tauri.app/develop/debug/>.
2. Painel **Performance** com "Web Vitals" ligado e **Performance monitor** visível no rodapé.
3. Gravar exatamente as quatro interações de §2.2, com **CPU 4× slowdown** ligado para tornar visível qualquer quadro acima de 4 ms.
4. Em cada gravação, ler três números:
   - **Long tasks** e **loAF** (quadros > 50 ms) — quemMv them e com que `sourceURL`;
   - **Input delay** vs **processing duration** vs **presentation delay** da interação. Se o `input delay` domina, o problema é trabalho _de outra_ tarefa (o relógio de 60 s é o suspeito nº 1, `CalendarScreen.tsx:120-123`); se **presentation delay** domina, o problema é estilo/paint (§1.6) e a Fase P7 é a resposta.

`INP` é a métrica de alvo: da interação até o próximo quadro. O alvo do Google é **p75 < 200 ms**, com a divisão em três fases (input delay, processing, presentation delay) — <https://web.dev/articles/inp>.

### 2.4 INP e LoAF dentro do app (número que fica no repositório)

`web-vitals` **não é uma dependência de produção**. A medição é um script de desenvolvimento, importado só quando `import.meta.env.DEV`, com a árvore removida no build (o mesmo mecanismo de `data/dev-seed.ts:54`, cujo critério de aceite já é `rg "dev-seed" dist/assets` → vazio):

```ts
// src/lib/perf/dev-metrics.ts — só DEV; verificado por rg no dist
import { onINP, onLCP } from "web-vitals/attribution";
onINP((m) =>
  console.debug(
    "[inp]",
    m.value,
    m.attribution.inputDelay,
    m.attribution.processingDuration,
    m.attribution.presentationDelay,
  ),
);
onLCP(console.debug);
new PerformanceObserver((l) => {
  for (const e of l.getEntries()) {
    if (e.blockingDuration > 0)
      console.debug(
        "[loaf]",
        e.duration,
        e.scripts?.map((s) => `${s.sourceURL}:${s.name}`),

}).observe({ type: "long-animation-frame", buffered: true });
```

A atribuição por `long-animation-frame` é o que transforma "um clique demorou 400 ms" em "`CalendarScreen.tsx` levou 260 ms nesse quadro" — <https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/performance/identify-inp-causes.md>. Nenhum destes números vale sem um volume declarado. ### 2.8 O que **não** usar como instrumento

- **Lighthouse** — ele pressupõe rede e navegação de URL; num app `file://` sem roteador (`AGENTS.md:9`) os números de LCP/FCP não descrevem nada que aconteça. O LCP aqui é "quando o `index.html` pinta", e o gargalo real é o primeiro `invoke`. Usar `performance.mark`/`measure` em volta do `mount` e do primeiro `load`.
- **Benchmark sintético de `columnize`/`placeInDay` sem DOM** — mede o número que já sabemos medir e esconde o custo real, que é `Intl` + reconciliação + paint.

## 3. Decisões fechadas

### 3.1 Herdadas

D4 (tons de camada) · D6 (UTC + IANA, sem ajuste automático ao viajar) · D7 (sobreposição permitida, conflito derivado) · D11 (atraso derivado, nunca persistido) · D15 (uma escala de tempo só) · D15bis (cinco modos numa tela só) · D16 (densidade da grade) · D19 (modes são `useState`, não rotas) · INV-1..INV-7 · `AGENTS.md:9` (sem roteador) · `AGENTS.md:14-15` (a verdade do domínio é o Rust; quando TS e Rust divergem, Rust está certo) · `AGENTS.md:17` (`domain/` puro, com `Clock` injetado) · `AGENTS.md:19` (todo IPC por `src/lib/ipc.ts`).

**DP2 e DP3 são o teste de disciplina contra `AGENTS.md:17`:** memoizar um `Intl.DateTimeFormat` **não** é memoizar domínio. É cache de plataforma. Nenhuma regra de domínio entra num cache de memoização, e nenhum cache de memoização entra no `domain/`.

### 3.2 Novas

**DP1 — Não recarregar o que já está em memória; a leitura é por janela, com cache invalidado por escrita.**
Decisão: `CalendarScreen` passa a ler por uma **camada de dados** (`src/features/calendar/data/calendar-store.ts`) com um cache `Map<WindowKey, WindowData>`, onde `WindowKey` é `"<mode>:<from>:<to>"`. Trocar de `agenda` para `semana` e voltar **não** gera `invoke`. Escritas (`moveOccurrence`, `completeItem`, …) invalidam por prefixo, nunca por leitura.
Justificativa: hoje a tela só tem `useState` e um efeito (`CalendarScreen.tsx:110-113`, `:154-194`), então qualquer volta no tempo custa dois `invoke` completos — incluindo a materialização completa do Rust (§1.5). É o custo mais fácil de remover e o que mais se paga em uso diário.
Alternativa rejeitada: `useSyncExternalStore` desde já (seria DP4 meio implementado e sem o backend que o sustente); `zustand`/`@tanstack/react-query` (duas dependências para um problema que é uma janela e um `Map`).
Consequência: o efeito de carga de `:154-194` vira uma assinatura de `useCalendarWindow(window)`; o cancelamento por `cancelled` (`:155`) sai junto, porque o cache resolve a corrida por construção.

**DP2 — `Intl` é infraestrutura, e infraestrutura é singleton de módulo.**
Decisão: um `Intl.DateTimeFormat` por par (locale, opções), criado uma vez, memoizado em `Map` no escopo do módulo. `formatClock` (`CalendarScreen.tsx:89-96`) e os cinco `new Intl.DateTimeFormat` em corpo de render (`:246`, `:251`, `:385`, `:520`, `:610`) passam a usar um formatador de módulo. `ItemPanel` (`:794`) deixa de usar `toLocaleTimeString` e passa pelo mesmo caminho.
Justificativa: `domain/time.ts:97-114` **já** faz exatamente isso (`formatterCache`) e funciona. A UI reintroduziu o padrão errado em seis lugares. É a mudança de melhor razão por byte em toda a lista, e não toca em nenhuma regra de domínio.
Alternativa rejeitada: formatar tudo por `date-fns` (é a dependência morta de §1.1 e traz 4 MB para resolver o que `Intl` já resolve); pré-formatar os rótulos no `GridItem` vindo do Rust (violaria `AGENTS.md:14`: formatação é apresentação, e o backend não deve conhecer locale da UI).
Consequência: `formatClock` deixa de ser "puro por acidente" e passa a ser determinística; os testes de `domain/` não mudam porque `time.ts` já é memoizado.

**DP3 — Estado que muda a 60 s não propaga para a grade; a grade não é re-renderizada por relógio.**
Decisão: `WeekView` **não** recebe `now`. A linha do momento vira um componente isolado (`ui/NowIndicator.tsx`) que sozinho consome o relógio de 60 s e escreve **uma** propriedade (`style.top`) em um elemento que já existe. `MonthView` recebe apenas a data de "hoje" como `string`, que muda uma vez por dia.
Justificativa: hoje `setNow` (`:121`) invalida cinco visões (`:306`-`:329`) e força o re-cálculo completo de §1.3 a cada minuto, sem que nada tenha mudado. E é por isso que **memoizar `WeekView` não resolveria nada**: enquanto `now` for prop, a memoização nunca acerta. Separar o relógio é o que torna a memoização possível.
Alternativa rejeitada: baixar o intervalo para 1 s (pior); `useDeferredValue` sobre `now` (a linha do momento ficaria atrasada, que é pior que renderizar); `memo(WeekView)` sem DP3 (memo que nunca acerta é só `memo`, custo sem benefício).
Consequência: a assinatura de `WeekView` encolhe (`days`, `byDay`, `scale`, `onSelect`); `AgendaView` e `ListView` passam a receber `today: PlainDate` em vez de `now: Instant`, e só `ListView`/`PlanningView` — que derivam atraso por `isOverdue` (`domain/overdue.ts:16`) — continuam precisando do instante, com memo próprio.

**DP4 — A ponte vira assíncrona, e a materialização deixa de ser efeito colateral da leitura.**
Decisão: em duas partes. (a) Todo `#[tauri::command]` que toca o banco passa a `async fn`, movendo o trabalho para o pool de `async_runtime`. (b) `materialize_occurrences` (`commands.rs:191-270`) para de rodar em **toda** leitura: passa a rodar só quando a janela ainda não está materializada (um marcador em `setting`, ou `SELECT 1 … LIMIT 1` sobre a faixa), com o resto do trabalho corrigido na Fase P4 (parse de `exdates` fora do laço, `HashSet`, `new_id()` só quando o `INSERT` é mesmo necessário, e um índice que permita filtrar séries pela janela em vez do `OR r.id IS NOT NULL`).
Justificativa: a documentação do Tauri é explícita — comando sem `async` roda na thread principal (<https://v2.tauri.app/develop/calling-rust/>). Uma leitura que hoje pode expandir ~730 dias por regra e parsear JSON por ocorrência **é** um congelamento de janela esperando para acontecer. E o comentário em `commands.rs:188-190` ("pode acontecer em toda leitura de janela sem custo correto a pagar") está errado no que importa: o custo é evitável, não apenas tolerável.
Alternativa rejeitada: `#[tauri::command(async)]` com corpo síncrono (Tauri aceita, mas `State<'_, Db>` emprestado impede a assinatura `async` — a limitação está registrada em <https://github.com/tauri-apps/tauri/issues/2533>); `spawn_blocking` manual em volta de `db.write` (resolve, mas esconde a intenção; `async fn` é a forma idiomática); cache só em Rust com TTL (não invalida por escrita, que é o caso que importa).
Consequência: `#[tauri::command] pub fn …` vira `pub async fn …` em `commands.rs`; `*_core` continua síncrono e testável (`commands.rs:9-11`), porque a separação em duas camadas já existe e é o que mantém os testes sem Tauri. Verificar que nenhum comando novo toma `State<'_, T>` **e** usa valor emprestado na assinatura assíncrona.

**DP5 — Sem virtualização deialize agora; com virtualização só depois de P5 medir.**
Decisão: **não** adicionar `@tanstack/react-virtual` nesta spec. A Semana tem ~144 nós fixos e a contagem total é saudável (§1.7). O gargalo medido é trabalho por render, não contagem de DOM. Virtualizar uma grade de altura **fixa** (`visibleHeight = (24 − 6) × 56 = 1008px`, `domain/grid-scale.ts:42-44`) traria um problema novo: `content-visibility`/containment em item posicionado por `top`/`height` absolutos interage mal com o eixo `sticky`, e o ganho seria de alguns milissegundos frente aos ~8–21 ms do trabalho de `Intl`.
Justificativa: virtualização é a resposta certa para **muitas linhas de altura variável**; aqui a altura é fixa e conhecida, e a quantidade de nós é pequena. Precipitar a dependência (≈ 30 kB) e a complexidade de _lane management_ (`directDomUpdates`, eixos cruzados, `measureElement`) para poupar 2 ms seria otimizar no escuro.
Alternativa rejeitada: `content-visibility: auto` nas 42 células do Mês agora (isolado em P5, porque _containment_ em item de grid precisa de `contain-intrinsic-size` para não dançar a barra de rolagem — <https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Using>); library de calendário pronta (resolveria D15/D16/D18, que já estão fechadas).
Consequência: **P5 é um gate.** Se o perfil mostrar paint como dominante com 500 ocorrências, aí sim `@tanstack/react-virtual` entra em fase própria, com a semana orientada por eixo **vertical** (18 faixas de hora, altura fixa 56px — o caso canônico do virtualizador).

**DP6 — A fronteira de estado é `items`, não o estado da tela.**
Decisão: `selected` sai do estado que controla a grade. A Semana passa a ser `WeekView` (ou `WeekGrid`) + `TimedItem`, e `setSelected` só altera o `ItemPanel` (`CalendarScreen.tsx:335`). Toda alteração que **não** muda `items`/`byDay`/`days` não chega à grade. `byDay` ganha um comparador por identidade de conteúdo, para que uma releitura que devolve o mesmo conjunto não invalide os filhos.
Justificativa: clicar num item e pagar 8–21 ms de recálculo (§1.8) é o defeito de interação mais visível do app. A correção não é `memo` — é não ter o estado no lugar errado. O mesmo vale para `now` (DP3) e para o relógio.
Alternativa rejeitada: `memo(WeekView)` com `now` ainda como prop (DP3 mostra que nunca acertaria); `useState` de seleção elevado para um store (DP4 não pede store ainda).
Consequência: `WeekView` e filhas precisam ser `memo` **e** receber apenas props estáveis — `onSelect` (`useCallback`), `byDay` (identidade estável enquanto o conteúdo não muda), `days` (já memoizado, `:196`), `scale` (constante de módulo, `:70`). É por isso que DP6 vem **antes** dos `memo` da Fase P3.

**DP7 — `backdrop-filter` só onde o conteúdo por trás realmente rola; e nunca em `width`/`height`/`top`/`left`.**
Decisão: (a) o cabeçalho fixo da Semana (`:372`) e o eixo de horas (`:406`) trocam `backdrop-blur` por fundo **opaco** — o conteúdo por trás é a própria grade, conhecida e estática na horizontal; (b) `.vibrancy` permanece em `aside` e `header` do shell (é a assinatura visual do produto, e o conteúdo por trás muda pouco), mas a `transition-[width]` da `aside` (`:192`) vira animação de `grid-template-columns` ou `transform`, nunca de `width`; (c) **proibido** `transition` em `width`, `height`, `top`, `left` e `box-shadow` no produto — a regra entra no `AGENTS.md` junto com o resto.
Justificativa: `backdrop-filter` obriga reamostragem da região por trás **a cada quadro**; numa grade que rola, isso é por pixel de rolagem. São quatro superfícies com blur ativas ao mesmo tempo (§1.6). E `transition` em propriedade de layout é o padrão clássico de quadro perdido em WebView2.
Alternativa rejeitada: trocar `.vibrancy` por `background-color` em tudo (mata a assinatura visual do produto, que é decisão de design e não de performance); `will-change: transform` na `aside` durante a animação (promove, mas não remove o layout por quadro — e cria uma camada permanente se mal Cleanup).
Consequência: `styles.css:186-189` continua existindo; muda **onde** é usada. `prefers-reduced-motion` (`styles.css:168-176`) permanece como está.

**DP8 — Métrica de aceite é número, não adjetivo.**
Decisão: toda fase desta spec tem um critério mensurável e um volume declarado (§2.7). Nenhuma fase é aceita com "ficou mais rápido". Se o número não foi medido na máquina de referência, a fase não passou.
Justificativa: performance é a única área em que "parece que melhorou" se prova errado com frequência suficiente para que o número seja o critério, não a conclusão.
Alternativa rejeitada: aceite por inspeção visual do DevTools (é o que faz este trabalho virar adivinhação).
Consequência: os números de §4 são o contrato; se a P0 mostrar que uma estimativa estava errada por ordem de grandeza, **corrige-se a estimativa nesta spec** e não se relaxa o critério.

**DP9 — `sideEffects: false` fica; code-splitting só onde houver fronteira real.**
Decisão: `package.json:4` (`"sideEffects": false`) **não** muda — é correto e o Rolldown respeita. Não há `React.lazy` nesta spec: com um `App` só e cinco modos como `useState` (`AGENTS.md:9`, D15bis), o único chunk é a verdade, e dividir 118 kB gzip em duas requisições num `file://` é trocar parse por I/O sem ganho. O que entra é: (a) remoção da dependência morta `date-fns`; (b) um `build` de perf opcional com `sourcemap: true` para que produção seja perfilável (§1.1).
Justificativa: `manualChunks` numa SPA de uma rota é cosmético. O custo real do arranque é o `<link>` externo de fonte (§1.1), não o número de arquivos no `dist`.
Alternativa rejeitada: `React.lazy` nos cinco modos (quebraria o "trocar de leitura não custa carregamento" de D15bis, e cada modo é uma tela só); remover `sourcemap: false` (sem isso não há atribuição de quadro em produção).
Consequência: `P6` mexe em `package.json` (remove `date-fns`) e em `vite.config.ts` (sourcemap condicional). `sourcemap: false` continua o padrão do build de entrega.

**DP10 — Cache de dados tem dono, forma e invalidação; não é uma coleção de `useMemo`.**
Decisão: o cache de DP1 é um módulo com `Map` privado, chave composta e API de três funções (`read(window)`, `invalidate(prefix)`, `clear()`). Ele **não** é um store de estado global, não é um contexto React, e não expõe `useSyncExternalStore` nesta spec. Quando a spec 05 (Google Calendar) trouxer sincronização por evento, aí sim entra `useSyncExternalStore` — com `getSnapshot` **estável por referência** e seletor memoizado, que é o requisito documentado da API, não uma convenção: <https://react.dev/reference/react/useSyncExternalStore>.
Justificativa: `useSyncExternalStore` aqui seria um store com um consumidor e sem eventos para consumir. Introduzi-lo agora cria uma abstração que a spec 05 vai ter que reorganizar.
Alternativa rejeitada: contexto React com `useMemo` no valor (contexto não memoizado é a causa nº 1 de re-render em árvore grande, e aqui seria um store com um consumidor); Zustand (dependência nova para um `Map`).
Consequência: `P1` entrega um módulo testável por `node --test`, sem React nenhum — coerente com `AGENTS.md:17`: o cache é **dados**, não domínio, então vive em `data/`, não em `domain/`.

## 5. Riscos e o que **não** fazer

**Anti-padrões, com o motivo pelo qual cada um está nomeado aqui:**

1. **`memo` como default.** O critério de aceite de P3 exige explicitamente `React.memo` **ausente** de `NavItem`, `Panel`, `Metric`, `TodayView`, `KanbanView`, `ListView` e `SubjectView`. Envolver componente sem custo em `memo` é pagar comparação de props em todo render para não ganhar nada. `Panel` (`App.tsx:486`) recebe `className` string e `children` — nunca re-renderiza de forma que o memo ajude.
2. **`useMemo` em tudo.** `App.tsx:172-178` filtra **4 itens constantes de módulo** dentro de um `useMemo` — o memo custa mais que o filtro. O mesmo vale para `layerClass` (`domain/layers.ts:61`, já um `Record` — não precisa de memo) e para os `useMemo` de 1 elemento em `CalendarScreen.tsx:196` (`days`, 7 itens, de um laço puro — reads melhor inline, e o ganho de identidade é questionável). **Regra:** `useMemo` onde a conta é O(n) sobre dado que muda, e o resultado é identidade usada como dependência ou prop.
3. **Memoizar antes de mover o estado.** `memo(WeekView)` **antes** de DP3/DP6 é memo que nunca acerta, porque `now` muda a cada minuto e `selected` a cada clique. A ordem de P3 é intenciva: (a) relógio, (b) props, (c) só então `memo`.
4. **React Compiler antes da Fase P3.** O React Compiler 1.0 é estável desde 2025-10-07 e memoiza automaticamente, e o Vite 8 tem caminho de preset explícito para ele — mas é **opt-in**, e a documentação do React para código existente é "pode deixar a memoização manual como está, ou remover só depois de testar bem". Aqui, memoizar na mão o que o compilador faria é redundante, e ligar o compilador às cegas antes de haver baseline e testes de snapshot seria trocar um problema mensurável por outro não mensurável. **Reavaliar em P7**, com número ao lado.
5. **Cache de dados sem dono.** Um cache que não tem `invalidate` explícito por escrita é um bug de consistência com prazo de validade. `domain/` não pode ser cacheado por janela (é regra pura e já é testada); `data/` pode, desde que a chave seja explícita.
6. **Cache em `getSnapshot` instável.** Se e quando `useSyncExternalStore` entrar (spec 05), `getSnapshot` tem que devolver **a mesma referência** enquanto nada mudou, senão loop de render. Está documentado: <https://react.dev/reference/react/useSyncExternalStore>.
7. **Virtualização preventiva.** Ver DP5. `@tanstack/react-virtual` adiciona ~30 kB, um eixo de gestão, e interage mal com `position: sticky` e com itens posicionados por `top` absoluto, para poupar milissegundos numa grade de altura fixa com ~150 nós. **Só depois de P5.**
8. **`will-change` em tudo.** `will-change` cria camada de composição permanente. `will-change` sem limpeza custa memória e memória de GPU. A regra é: só durante a animação, e removido no fim.
9. **Paginar a janela de leitura como default.** Uma janela de 45 dias no modo `mes` que devolve 500 ocorrências cabe folgadamente em memória. Paginação aqui trocaria um render lento por 5 `invoke`. Paginação só entra se P4 mostrar payload acima do orçamento de §4.
10. **`Channel`/streaming para uma tela de calendário.** O volume de dados é de dezenas de KB. Streaming adiciona estado de conexão, reordenação e reassemblagem para um problema que não existe. `Channel` só faz sentido quando a spec 05 trouxer sincronização com push do Google.
11. **Mover regra de domínio para o TS para "economizar IPC".** Proibido por `AGENTS.md:14-15`. Se um cálculo custa caro no Rust **e** no TS, a resposta é otimizar os dois ou mover o cálculo para um só — nunca manter duas versões e escolher a cara.
12. **`sourcemap: true` no build de entrega.** DP9 deixa o sourcemap como opt-in por `PERF=1`. Ele expõe código-fonte no artefato.
13. **Confundir "sem re-render" com "sem trabalho".** Remover `StrictMode` (`main.tsx:12`) faria o dev medir bonito e o usuário não sentir nada. `StrictMode` fica.

**Riscos reais desta spec:**

- **Regressão de consistência na P1.** Cache por janela sem invalidação completa devolve item que foi movido. Mitigação: a API de invalidação é prefixal e testada; toda escrita passa por ela antes de a UI tocar o store.
- **Regressão de corretude na P4.** Mover `materialize_occurrences` para sob demanda muda a **observabilidade** da materialização: `list_events_in_window` passa a poder devolver menos linhas na primeira leitura de uma janela nunca lida, se o marcador estiver errado. Mitigação: o marcador só é gravado **depois** do commit bem-sucedido, e `cargo test` ganha um caso que materializa a mesma janela duas vezes e compara.
- **Regressão de domínio na P4.** `expand_rule` (`commands.rs:290`) é a verdade da recorrência (D6, D10). Otimizá-lo é mexer em regra. Mitigação: os testes de `commands.rs` existentes são a rede; **nenhum** caminho de cálculo muda — só o custo de chegar lá.
- **Fadiga de rotação.** P2..P6 são seis mudanças pequenas em código que funciona. O risco maior desta spec é ser abandonada pela metade. Mitigação: cada fase é < 100 linhas e tem aceite de um comando; nenhuma depende de fase posterior.
- **O estimate de §1.8 pode estar errado.** DP8 trata isso explicitamente: corrige-se a estimativa, não o critério.

## 8. Fora de escopo

- **Otimização da Home** (`TodayView`, `KanbanView`, `ListView`, `SubjectView` de `src/App.tsx`). São mock com dados de módulo; o custo por render é desprezível e o custo por carregamento é zero. Quando a Home virar dados reais, esta spec é reavaliada.
- **`CalendarScreen` continuar mock de leitura.** As cinco visões já existem; o que falta é arraste, edição e criação (spec 02). O volume de 200/500 ocorrências do §2.7 é o que torna esta spec aplicável hoje.
- **Tamanho do executável Tauri** (o binário Rust, o amalgamation do SQLite em `rusqlite = { features = ["bundled"] }`). É decisão de distribuição, não de render, e mexer nisso mexe em `tauri:build` e no instalador NSIS.
- **Acessibilidade como métrica de performance.** `prefers-reduced-motion` já é respeitado (`styles.css:168-176`) e DP7 não enfraquece isso; otimizar removing animação sem manter o caminho de teclado e leitor de tela não é otimização.
- **Multiusuário, concorrência e cache HTTP.** App desktop mono-usuário com banco local (`db.rs:62-65` já registra essa premissa).
